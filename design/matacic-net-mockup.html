Exposing a homelab service with Cloudflare Tunnel — no open ports

cloudflare self-hosting networking

Every service I run at home used to end the same way: one more port forward on the router, one more thing to remember when something breaks at 23:00. A Cloudflare Tunnel removes the inbound rule entirely — the host dials out, and nothing on the WAN side listens.

Why not port forwarding

An open port is a permanent commitment: TLS certificates, a dynamic IP, and an exposed service you now have to patch on someone else's schedule. The tunnel moves that surface to Cloudflare's edge.

Installing cloudflared

On a Debian host, add the repository and install the daemon, then authenticate against the zone:

bash Copy 
cloudflared tunnel login
cloudflared tunnel create homelab
cloudflared tunnel route dns homelab grafana.matacic.net

Named tunnels vs. quick tunnels

Quick tunnels are fine for a five-minute demo. Anything you intend to keep should be a named tunnel with credentials on disk and a systemd unit, so it survives a reboot without you.

Takeaway: if the only way into your network is outbound, an inbound misconfiguration cannot exist.

Filtering journalctl to a single unit and boot

Scrolling the whole journal to find one service's last failure is wasted time. Scope it to the unit and the current boot, and the noise disappears.

bash Copy 
journalctl -u cloudflared -b -p warning --no-pager

Add -f to follow it live, or -b -1 to read the boot before the reboot that hid the evidence.
